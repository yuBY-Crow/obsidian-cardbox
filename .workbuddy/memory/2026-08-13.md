## 新建卡片下部自适应贴合输入法键盘（v0.6.26）

用户要求：卡片下部自动贴合输入法 UI 顶部。

**实现**（CaptureModal.bindKeyboard）：
- 监听 window.visualViewport 的 resize + scroll
- 键盘高度 = window.innerHeight - visualViewport.height
- keyboard>0 时 modalEl.style.transform = translateY(-keyboard px)
- 收起清空复位，transition 0.15s 平滑，onClose 清理

**平台差异**：iOS innerHeight 不变、vv 缩小（靠这个计算）；
Android adjustResize 两者同步缩 → keyboard≈0，系统自动处理，不重复顶。

**配合 CSS**：
- .cardbox-capture-container（= modalEl.parentElement = .modal-container）
  手机端 align-items: flex-end（之前 Obsidian 默认 center 居中，卡片悬中间不贴底）
- .cardbox-capture-modal 手机端 width 100% + max-height calc(100vh - 60px)

**测试经验**：keyboardtest 必须：
1. 页面里注入 styles.css（否则 align-items flex-end 测不到）
2. 假 visualViewport 用 `get height(){return mockVvHeight}` getter，
   手动改 mockVvHeight 后触发 listeners 模拟键盘弹出/收起

全量 300 例通过（keyboardtest 6 例新增）。版本 0.6.26，提交 0de3ecb。

## 键盘贴合修复：改用 Platform.mobileKeyboardHeight（v0.6.27）

用户反馈微信输入法弹出后卡片底部仍不贴键盘。

**根因**：v0.6.26 用 `window.innerHeight - visualViewport.height` 算键盘高度，
但 Android adjustResize 下两者**同步缩小**，差值 = 0，永远算不出键盘高度。
微信输入法正是这种场景（visualViewport 不变或同步缩）。

**正确信号（关键知识）**：Obsidian 移动端内置了
`Platform.mobileKeyboardHeight` / `Platform.mobileSoftKeyboardVisible` /
`Platform.mobileDeviceHeight`（官方 .d.ts **未导出**，运行时存在，
社区 @obsidian-typings 的 PlatformEx 类型证实）。这些由 Obsidian 内部
Capacitor Keyboard 插件维护，特殊键盘也正确上报，不依赖 WebView。

访问方式：`(Platform as any).mobileKeyboardHeight`。

**新逻辑**：
1. 键盘高度优先取 Platform.mobileKeyboardHeight（visible 时），
   visualViewport 差值仅兜底
2. 上移量 = keyboard − (deviceHeight − innerHeight)：减掉 adjustResize
   已缩小的量，避免双重上移
3. 属性值无事件 → 150ms 轮询 + resize/scroll 即时响应

**测试**：keyboardtest 重写为微信输入法场景（vv 不变、仅 Platform 上报），
证明旧方案测不出这个真实失效。全量 300 例。版本 0.6.27，提交 c061833。

**经验**：处理 Obsidian 移动端键盘，首选 Platform.mobileKeyboardHeight，
不要自己算 visualViewport（Android adjustResize 会失效）。

## 键盘贴合彻底修复：Capacitor keyboardWillShow 事件（v0.6.28）

微信输入法两版都没上移，搜索确认真相：

**根因**：Obsidian 移动端 Android 用沉浸式全屏（edge-to-edge，见官方
v1.9.10 更新日志），触发 Capacitor 已知 bug——**全屏模式下键盘无法调整
WebView 大小**。所以 `window.innerHeight` 和 `visualViewport.height`
都不变，差值永远 = 0，前两版的信号都失效。

v0.6.27 的 shrink 补偿还有隐藏 bug：`mobileDeviceHeight` 缺失时回退
`screen.height`（物理像素），shrunk 巨大 → translate 被 clamp 成 0。

**正确信号（终极答案）**：`window.Capacitor.Plugins.Keyboard.addListener
('keyboardWillShow', info => info.keyboardHeight)` —— 社区插件公认权威，
微信输入法也通过系统 WindowInsets 正确上报。

**新逻辑**：Capacitor 事件主信号 + Platform/visualViewport 轮询兜底 +
取最大值 + 去 shrink 补偿 + Android 物理像素转 CSS（÷devicePixelRatio）。

**测试**：keyboardtest 重写为「innerHeight 不变 + vv 不变 + 仅 Capacitor
事件上报 340」的真实微信输入法场景。全量 300 例。版本 0.6.28，提交 2ec7a15。

**终极经验**：Obsidian 移动端 Android 键盘适配，唯一可靠信号是
Capacitor Keyboard 事件，不要依赖 innerHeight/visualViewport
（沉浸式全屏下它们都不变）。

## 键盘贴合真机日志定位根因（v0.6.32）—— 终于找到

用户提供真机日志（LogModal 复制的），精确定位：

```
keyboardWillShow 触发 {"raw":319, "css":106.33}
视口快照 {"innerH":890, "dpr":3}
Platform 内置值 {"vis":false}   ← 注意 pkH/deviceH 都 undefined
```

**根因**：toCssPx 把 Capacitor 上报的 keyboardHeight（319，**已是 CSS
像素/dp**，319/890≈36% 正是键盘占比）又除以 dpr=3 → 106px，上移量
严重不足，footer 仍被键盘遮住约 200px，看起来「没上移」。

**关键认知**：
1. Capacitor 的 keyboardHeight 在 Android/iOS 都是 **CSS 像素（dp）**，
   直接使用，不要除以 devicePixelRatio！
2. Platform.mobileKeyboardHeight / mobileDeviceHeight 在真机是
   **undefined**（之前 Platform 方案必然失效）
3. Capacitor 事件是唯一可靠信号（cap=true / kb=true / addListener=function）

修复：toCssPx 直接 return px。keyboardtest 改 dpr=3 + 上报 319 →
断言 padding-bottom=319px。

**经验**：真机日志（内置 logger + LogModal）比反复盲改高效百倍，
一轮就定位到 dpr 单位转换错误。全量 300 例。版本 0.6.32，提交 e5e7424。

## 卡片上移改用 fixed 定位 + bottom（v0.6.35）

真机日志证明 JS 全对（keyboard=319、cardH=551、paddingBottom=319px），
但视觉没生效 → 问题在 CSS 布局层。

**根因**：padding-bottom + align-items:flex-end 依赖 .modal-container

依赖它做定位会踩坑。给 modal 自己设 fixed 定位最可靠。

## 编辑器/标题框字体对齐 Obsidian 正文（v0.6.46）

编辑器正文(.cm-editor)和标题框(.cardbox-capture-title)之前用
var(--font-interface)（界面字体），与 Obsidian 正文默认字体
var(--font-text)（文本字体）不一致。

改为 var(--font-text)，去掉硬编码 fallback，完全跟随用户
「外观→文本字体」设置（含自定义字体）。

**关键认知**：Obsidian 两个字体变量的语义——`--font-interface` 是 UI
控件/界面字体，`--font-text` 是正文（编辑+阅读）字体。正文输入区必须用
`--font-text` 才对得上用户看到的正文效果。版本 0.6.46，提交 b3e6854。
